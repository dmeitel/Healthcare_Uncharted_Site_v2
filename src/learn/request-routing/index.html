Method Clinical informatics

Informatics work: routing requests.

I run a clinical informatics team, and every ask that reaches us gets one of four labels before anyone opens the build: break/fix, enhancement, optimization, or net new. It sounds like paperwork, and it is still the fastest consequential decision we make all day. The label picks the queue, the approver, and the owner, and a wrong label sends all three to the wrong place at once.

Principle The class is not a description of the work. It is the routing decision. By the time you have named it correctly, most of the arguing is already over.

The job

Where informatics sits.

Clinical informatics is the trade of sitting between the people who deliver care and the people who run the system, fluent in both directions. I translate a nurse's "this is broken" into a build requirement, and a build constraint back into language a unit can use. Open any card for what that group owns and when the work crosses to them.

Owns sequencing across teams and the yes on region and enterprise change. Everything net new lands here. Our job: it arrives classified and scoped, so the meeting can argue about order.
The care side
Own what correct care looks like on the unit. They confirm the baseline in a break/fix and the outcome in everything else, and the customer consult is theirs at every scope.
Owns any change to clinical practice, whatever class the request wears. Leads clinical enhancements while informatics documents the workflow that results.
Own how the day actually runs at a site. They hold the authoritative answer on operational requests and the approval at site scope.
The junction
Owns the workflow: what the system should do for the person at the bedside. We triage every request, run the classification, define the requirement, and validate that what shipped matches what care needed. We rarely hold the build keys, and we always hold the accountability.
The build side
Owns the records and executes the change: corrections, new records, the whole configuration surface. Informatics defines the requirement; applications makes it exist.
Owns servers, printers, the network, and the plumbing underneath the applications. Failures that turn out to be infrastructure hand off here after triage.
Owns the medical devices and the interfaces that carry their data into the chart. A vent that stops sending data is theirs. The flowsheet that stops showing it starts as ours.

Every request crosses at least one of these seams. The standard below exists because seams are where work gets lost.

One pipeline, two levels of routing.

Requests reach an informatics team through four doors: the ticket queue, email, chat, and the follow-up somebody promised in a meeting. Whatever the door, they converge on a single classification point before any analysis starts. Analysis and design produce a tested set of options. Change control settles approval and the production timeline. And implementation is finished when production behavior is verified, which is a stricter bar than "launched."

The lifecycle, step by step

Every class walks the same eight steps. What changes by class is where the work is tracked, who leads it, and how far the approval reaches. The sequence itself never changes.

Level 1 · Three tests, four classes

Class comes from three questions asked in order, stopping at the first yes. Each one is answerable by inspecting the existing build. That constraint is deliberate. A test you answer by looking produces the same class no matter which analyst is on triage that day.

The classification tree
Stop at the first yes
Pick a class below and the tree lights its path. Optimization is the fall-through: everything the change touches already exists, so no test fires.
One modifier. When an enhancement or a net new build is bigger than the team can absorb inside its normal cadence, it gets designated a PROJECT. A project manager takes the lead, and the demand record becomes the system of record. Break/fix and optimization never ride that track.

A process that was operating as designed has stopped.

Break/fix outranks everything else in the queue, because an established workflow is interrupted and clinical or operational work is impeded right now. The root cause, an upstream system change, an interface failure, a version upgrade, gets identified during analysis and has no bearing on the class. A request for capability that was never built fails Test 01 and goes back through the tree.

Case file · Break / fix
"The vent flowsheet on 4 West stopped totaling intake and output overnight. It was fine yesterday."
The tests

Operating as designed, and now it isn't. Test 01 says yes, and the tree stops there.

The route

Incident, shared with applications. We reproduced it on a test patient, compared against 3 East where totals still ran, and found an overnight upgrade had changed a calculation record.

The close

The first correction fixed the totals and quietly broke a different column, so it went back to option development. The second option verified on the next shift. That detour is the dashed loop from the pipeline, live.

Governance

System of record
An incident in the ticketing system, shared between informatics and the applications team.
Responsible party
Informatics triages and defines the workflow break. Applications owns the build correction. Technical services or biomedical engineering take it when the failure is hardware or an interface.
Approval path
Customer consultation before anything moves in production. Governance rarely enters the path.

Execution sequence

  1. Establish the expected workflowThe documented baseline comes first. You cannot declare a departure from a design nobody wrote down.
  2. Reproduce the failureCapture the user, the context, and the exact step where behavior diverges.
  3. Compare against a functioning equivalentThe same build in another department, or the same order in another location. The delta is usually the answer.
  4. Develop and test corrective optionsConfirm each candidate resolves the failure without introducing a second one.
  5. Consult the customer, then implementTesting, education, and ticket documentation all precede the production move.
  6. Verify in production, then closeOn failure: back out, correct before closure, or withdraw and return to step 04.

The capability is owned and installed, but delivery needs records that do not exist yet.

Enhancement covers work that extends existing build by creating new records or new record types: a new worklist, a new note template, a new order set. The change adds to the technical footprint, so the applications team creates the build ticket and links it to the change record. That link is what keeps the addition visible a year from now.

Case file · Enhancement
"New bronchoscopy service starts next month. We need an order set and a procedure note."
The tests

Ordering and documentation are owned and installed, and the records for this service do not exist. Test 03 says yes.

The route

A task linked to the change record. We wrote the requirement with the physician champion, applications built the records, and the customer group confirmed priority at the weekly review.

The close

Launched with education ready, verified on the first live case, then closed. The footprint grew, and the change record says exactly where.

Governance

System of record
A task in the ticketing system. Applications creates the build ticket and links it to the change record.
Responsible party
Informatics owns workflow configuration enhancements. Changes to a clinical standard are led by a physician champion working with the applications team.
Approval path
Customer consultation in all cases. Governance joins according to scope.
Cadence
A weekly team review for sizing and sequencing, then a weekly or biweekly review with the customer group to confirm priority.

Execution sequence

  1. Establish the desired outcomeThe operational result required, which is a different thing from the solution the requester proposed.
  2. Confirm understanding with the requesterRestate the requirement in writing or in session before build work begins.
  3. Identify affected records and record typesThis inventory confirms the classification and scopes the applications effort in one move.
  4. Develop and test optionsConfirm the change delivers the outcome without downstream effect.
  5. Approval and production timelineTest plan, education material, and ticket documentation completed before launch.
  6. Launch, verify, closeClosure follows verified production behavior. Implementation alone earns nothing.

Everything the change touches already exists.

Optimization adjusts values on records currently in the build: modify schedule hours, correct displayed text, add an option to a note that already has options. No record gets created and the technical footprint holds still, so the approval path is correspondingly short. It is still a required path.

Case file · Optimization
"Can you add 'family at bedside' to the options on the rounding note?"
The tests

The note exists, the option list exists, nothing new gets created. Three noes, and the fall-through lands on optimization.

The route

A planner task. The shared-use check mattered here: two other units chart on that same note, and both got consulted before the value changed.

The close

Changed, verified, and closed inside the week. It is the smallest class on the page, held to the same verification bar.

Governance

System of record
A task in the ticketing system, paced through the team planner.
Responsible party
Informatics, working with the site or operational owner.
Approval path
Customer consultation before production. Without exception, including the tiny ones.
The boundary with enhancement
Think carpentry. Driving another nail or straightening a slanted one is optimization. Adding a shelf is enhancement. New material decides it, whatever the hours say.

Execution sequence

  1. Identify the record and its current valueDocument the present configuration before altering it. Future you will need the before state.
  2. Determine shared useA record edited for one site changes behavior everywhere that record is referenced. This step is where quiet disasters get caught.
  3. Consult the customerBrief, required, and documented on the task.
  4. Implement, verify, closeVerification requirements do not scale down with the size of the change.
Visibility risk. Optimization and enhancement are the two classes with no incident or demand record behind them. Work that never lands on the planner has no enterprise footprint, so at review time it cannot be reported, prioritized, or defended. The work still happened, and no system anywhere records that it did.

The capability, module, or record type is absent from the current build.

Net new requests concern capability the organization has not bought or has not installed. They are managed as demand, and prioritization is held by a governance body outside the team. When a project manager is assigned, informatics moves to a supporting role and keeps responsibility for one thing that never transfers: whether the resulting workflow is actually correct.

Case file · Net new
"Radiology wants the AI triage module the vendor demoed last month. Can we just turn it on?"
The tests

The organization does not own it and has not installed it. Test 02 says yes, and "just turn it on" leaves the vocabulary immediately.

The route

A demand record. Governance holds prioritization; a project manager was assigned, so the team moved to support and kept ownership of workflow accuracy.

The close

Still open, and that is normal. Net new closes when governance sequences it, and sometimes the sequence says not this year.

Governance

System of record
A demand record. It lives outside the incident and task queues entirely.
Responsible party
The assigned project manager where one exists. Where none is assigned, informatics leads.
Approval path
The governance body. Prioritization and sequencing live outside the team, at every scope.

Execution sequence

  1. Establish meeting frequencyLarge efforts fail from irregular contact more often than from bad decisions.
  2. Create the demand recordThe point at which the request becomes visible outside the team.
  3. Settle who leadsProject manager assigned: the team supports, and schedule ownership transfers. No project manager: informatics leads the effort end to end.
  4. Fact finding, then approval and executionData collection and workflow documentation produce the option list. Follow-up is required, on a schedule, in writing.
Supporting is an active role. Handing the schedule to a project manager transfers the timeline. Responsibility for whether the workflow is right stays with informatics, and it stays there for the life of the build.

Level 2 · Domain and scope

Class alone cannot route a request. Domain identifies which discipline holds the authoritative answer. Scope establishes how far the change reaches, and with it, whether governance enters the approval path. So the routing decision is the combination of all three, and it takes about thirty seconds once the tests are answered.

Clinical
Protocols and practice
The physician champion and clinical leads. What correct care looks like is answered here and nowhere else.
Operational
Scheduling and resulting
Operations and site leads. The people who run the day own the answer about the day.
Technical
Hardware, software, interfaces
Applications, technical services, biomedical engineering. If it has a cable or a queue, it is theirs.

Scope · the approval ladder

Department
Customer and the department owner
Consult, then move. No governance step.
Site
Customer and site leadership
Effects on adjacent departments get reviewed before implementation.
Region
Customer, then governance review
Alignment across sites is confirmed before build.
Enterprise
Customer, then governance approval
The change becomes an enterprise standard. Prioritization is held by governance.

Two class modifiers ride the ladder. Break/fix runs an expedited path at every scope, because somebody's workflow is down. Net new needs governance at every scope, because the ask concerns capability the organization does not own yet.

Level 3 · Who leads, who builds

Class, domain, and scope generate forty-eight combinations. Nobody consults a forty-eight cell grid, and nobody should. The escape is noticing that the three variables answer different questions. Domain settles who holds the authoritative answer. Who leads and who builds falls out of class and domain together. Scope, on its own, sets how far the approval has to reach. That collapses the grid to twelve lead assignments and the one ladder above, and both fit on a page.

Precedence · when the routing does not resolve cleanly
  1. Project designation overrides the table. The project manager holds accountability and the demand record is the system of record. Informatics keeps responsibility for workflow accuracy.
  2. Domain decides the answer; class decides the lead. When the two point at different parties, the lead coordinates the request and the domain owner defines what correct looks like.
  3. A change to clinical standard is led by the physician champion, whatever the class. This overrides the table, including for optimization.
  4. When the lead has no build access for the target record type, applications executes and the lead validates. Accountability does not transfer with a login.
  5. An unassigned request escalates. Where no party accepts the lead, it goes up to governance before it goes stale. An open request with no owner is the one state the standard forbids.

Why it's built this way

The arguments behind the rules, for when somebody pushes back. Open the one you need.

Classification precedes analysis

The class determines the system of record, the approval path, and the responsible party, and those three diverge immediately. A break/fix becomes an incident shared with applications. An enhancement becomes a task tied to a change record. A net new request becomes demand and leaves the team's hands entirely. Misclassify, and the work lands in the wrong queue, in front of the wrong approver, under an owner who never agreed to own it. Every step after that inherits the error and compounds it.

The enhancement line is drawn in records

Effort estimates are contested; build inspection is not. Ask whether a change is big or small and you get a meeting; ask whether it requires a new record and you get an answer, the same answer, from any analyst who opens the build. A test two people can apply identically is the only kind that survives a busy week.

The carpentry version holds up in every argument I have had about it. Another nail or a straightened slant is optimization; a new shelf is enhancement. The presence of new material is what decides, and the hours are a separate conversation.

Break/fix depends on a documented baseline

The break/fix test is comparative. "It stopped operating as designed" requires a written design to compare against, and where the expected workflow was never documented, the classification defaults to whoever argues most forcefully. You can predict what happens next. Requests for capability that never existed arrive dressed as failures, jump the queue on incident priority, and burn the exact hours the real incidents needed.

This is the point where the build knowledge base stops being a nice-to-have. The classification standard depends on it.

Class, domain, and scope stay separate

Each answers its own question, and conflating them is the main source of routing disputes with partner teams. Two requests can share a class and a domain and still need entirely different governance, because their scope differs. Held separate, a disagreement becomes locatable: the parties can name which of the three variables they read differently, and argue about that one. Merged into a single judgment call, the same disagreement is just two teams repeating their conclusions at each other.

Customer consultation is invariant; governance is conditional

Governance participation varies by class and scope, so it gets judged per request. Customer consultation never varies. The people executing the workflow hold information about the practical effect of a change that you cannot recover from the build, no matter how carefully you read it. A change that is technically correct and disrupts established practice has still failed, and a correct build does not overturn that.

Closure requires verified production behavior

Verification is a decision point with three live outcomes: back out, correct before closure, or withdraw and return to option development. All three are normal, and the standard says so out loud, because a team that treats backing out as failure will stop reporting the failures. Close a ticket on the assumption of success and the change leaves active tracking while its behavior is still unknown. You have converted a contained problem into an unattributed one.

What the standard cannot do

Prioritization across teams belongs to governance, and no routing table changes that. What the team controls is the state of a request when it arrives there: classified and scoped, with an owner attached. Get that right and the governance discussion is about sequence, which is a real discussion. Get it wrong and the meeting is spent arguing about definitions instead, and that argument comes back every month.

The point

The routing happens either way.

None of this is glamorous. A label, two lookups, a rule about closing tickets. But watch a team run without it. Every request gets negotiated from scratch and every closure is an assumption. The misses surface in the worst possible venue, which is an escalation with an executive on the thread.

"Unwritten, the routing still happens: in a hallway, settled by whoever argues loudest, and renegotiated the next time it comes up. Written down, it takes thirty seconds and a lookup."

Steal the tests. Redraw the table for your own team's seams, because yours sit somewhere different from mine. The specific assignments matter less than the move itself, which is to fix the answers to the questions you keep re-answering and save the arguing for the questions that deserve it.
